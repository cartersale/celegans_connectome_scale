# Review notes: code against the manuscript (2026-10-12)

I went through the repository as committed (e43d033) against the manuscript
(`1.tex`, "Connectome structure constrains neural activity across scales") and
`supp_material.tex` in the Overleaf export.  Everything below is a
static audit of the scripts and the library against what the two tex files say.

In short, the code is in good shape and the library core is correct. Below are some things you need ot chekc though.

## Text and code disagree

1. **Annealing proposals.** Methods says 60,000 proposals per search.
   `global_search.py` defaults to `--n-iter 40000`, and nothing in the README records
   a different value.
2. **Single-length operator intervals.** Methods says 500 cluster-bootstrap resamples
   with 50 random partitions rescored in each. `path_length_quotient.py` defaults to
   `--n-boot 200 --n-rand-boot 20`.
3. **Multi-member classes.** `1.tex` says 91, `2.tex` said 90. Nothing in the code
   asserts either, nor the 119 or 302.
4. **"Unsynapsed" has two definitions.** Every AUC, the degree controls and the
   Fig. 1D violin use no synapse from stimulated to responder
   (`src/conres/observables.py:45`). The Fig. 2A chord selection and the rho = 0.80
   quoted in the Fig. 2C caption "across unsynapsed pairs" use no synapse in either
   direction (`scripts/fig2_class_resolution.py:344`). The caption should say so.
5. **Non-default flags behind reported runs.** The 161-candidate, 70-pair predictive
   transfer is `functional_transfer.py --pool all --n-merge 70`, not the defaults
   (`--pool floor --n-merge 30`), and the primary merge criterion is
   `prospective_merges.py --min-degree 29`, not the default of no floor. The README
   gives the floors but not the transfer flags.
6. **Merge-trajectory script.** Methods' 20 trajectories match
   `class_merge_structural_loss.py`, which is what Fig. 2D and 2E read.
   `class_merge_trajectory.py` (30 trajectories) feeds no figure, yet it is the script
   the README names for "cell-class merge trajectories".

## Claims with no code behind them

These are stated as checks or validations, and no script performs them. Either the
code is in some `archive/` folder, not commited or on another machine and should be restored to `scripts/`, or the text need correcting.

- "Exact equitability tests ... are reported in the Supplementary Methods". No script
  performs a Weisfeiler-Leman refinement or any exact-equitability test, and the
  supplement has only the calibration.
- The amplitude validation: "It predicted detected responses with an AUC of 0.755 and
  correlated with the released response magnitudes at rho = 0.61 among the 1,025
  detected responses". `observable_resolution.py` builds amplitude and scores the
  operator against it, but nothing scores amplitude as a predictor of detection or
  against the released magnitude.
- "The resulting partition agreed exactly with the cell-class assignment distributed
  with the Randi et al. atlas on all 300 neurons". No script performs the comparison.
- "the transcribed memberships reproduce the published adjusted Rand index between the
  two partitions (0.105)". `dvali_communities.py` says in its docstring that the
  transcription should reproduce it and never computes the anatomy-versus-signaling
  index.
- The fly "reproduces the exact inverse to within 1.8e-8 when tested on the worm
  connectome" is `verify_metric_parity.py`, which prints the difference but asserts
  nothing. Fine as a diagnostic, but worth citing the log.

## Supplement sections the main text does not reach

`1.tex` points to the supplement for the exact-observation stratification, excision
and sham controls, the gamma calibration, the degree floors, the Dvali tables, the
other grouping methods, the lineage-only classes and the unc-31 comparison. It does
not point to the sections on sensitivity to alpha, dependence structures, spectral
normalisation, metric parity, or the functional interchangeability of class members,
although Methods describes the kappa analysis in full. Each needs a pointer, or the
section needs to stand on its own.

## Things I think you need to decide or report

These are not errors in the code. They are places where the analysis, as implemented,
supports a different statement from the one the text makes.

- **Two settings were chosen after seeing the contrast.** Methods already says the
  degree floor was dropped for predictive transfer because, with it in place, random
  partitions lost only 7.6%. The median floor for the merge criterion was chosen
  after running all four floors. Both are defensible, and both should be stated as
  choices made after the fact.
- **The fly spatial null has one hard-coded row.** Methods reports spatial clusters
  at every subdivision. `scripts/diagnostics/fly_spatial_null.py` computes four rungs
  and carries the f = 0.02 row as a literal (line 74). `fly_complexity_curve.py` does
  compute every rung, so the number exists, but the diagnostic does not reproduce it.
- **A verification script that cannot fail.**
  `scripts/diagnostics/verify_wormneuroatlas.py:135` hard-codes our three AUCs and
  the docstring says the closing sentence of the report is fixed text. As written,
  the cross-check reports agreement regardless of what our pipeline produces.
- **Chemical and electrical contacts are summed with equal weight everywhere.**
  Every analysis uses `build_matrix("all")`, signs are ignored, and the resolvent
  treats a gap junction as two directed edges. There is no chemical-only or
  electrical-only run anywhere. A reviewer will ask for one.
- **The observation denominator does not normalise labels.** `randi.build_occ3`
  (line 148) matches raw ROI labels against the node list by exact string, whereas
  `load_responses` and `build_correlations` (line 206) apply `normalise_name`
  first. A zero-padded label such as `VB01` would therefore drop out of the
  observed-pair set but not out of the response list or the correlations. One check
  against the raw label files settles whether any such label exists.
- **Degree-preserving surrogates break gap-junction symmetry.** `degree_controls.py`
  rewires the summed matrix as a directed graph, exactly as Methods describes, so
  the two orientations of a gap junction are swapped independently and the
  surrogates are not constrained to keep gap junctions symmetric. The z = 11.4 is
  therefore against a null that destroys one structural feature the real matrix has.
  Worth one sentence in Methods, or a symmetric-swap variant.

## Repository fixes

These are mechanical and I can make them if you would like, but I have not touched
anything.

- `README.md` and `claude.md` point at `docs/main.tex` and
  `docs/supplementary_methods_draft.tex`. The Overleaf names are `1.tex` and
  `supp_material.tex`, and `docs/` is gitignored.
- `pyproject.toml` cites `fig3_amq.py`, which does not exist, and lists `networkx`,
  which nothing imports. The `complexity_curve.py` docstring refers to "fig16, fig17,
  fig18".
- The README's command table should give the flags behind each reported run:
  `functional_transfer.py --pool all --n-merge 70`, `global_search.py --n-iter 60000`
  if that is what was run, and the `path_length_quotient.py` bootstrap flags.
- The README's merge-trajectory row should name `class_merge_structural_loss`.
- Panel scripts write to both `figures/supp` and `figures/supplementary`.
- `src/conres/observables.py` imports from two scripts through `sys.path`, so the
  package cannot be used without the scripts directory.
- Four scripts carry literal cross-check values: `HEADROOM = 0.1026` in
  `fig2_class_resolution.py`, the arm means in `fig4b_l1_adult_prediction.py`, the
  0.215 Jaccard in `fig4e_transfer_overlap.py`, and fixed worm reference constants in
  four diagnostics. A rerun with different seeds or `--n-rep` will silently mis-scale
  Fig. 2D/E or abort Fig. 4B. Reading these from the result files they come from
  would remove the trap.
- There are no tests. `assign_classes`, `gamma`, `quotient` and `build_occ3` are the
  load-bearing functions, and a short pytest file pinning 302 nodes, 119 classes, 91
  (or 90) multi-member classes, gamma = 0 on a planted partition and the quotient
  identity would catch most future regressions and settle item 3 above.
- `results/` is gitignored. The CSVs and logs are small, and the rule that every
  number in the text comes from a result file cannot be enforced while they live on
  one machine. I would track them, or at minimum snapshot them with the data on
  Zenodo at submission.
- The README lists the data files but gives no download steps for any of the six
  sources (Cook, Witvliet, Randi OSF E2SYT, Bentley, WormAtlas, FlyWire). The
  availability statement will not let a reader regenerate anything without a fetch
  script or at least URLs.
